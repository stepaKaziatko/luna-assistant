# Протокол shell ↔ core

JSON-RPC 2.0 поверх stdio дочернего процесса: одно сообщение — одна строка JSON. Shell запускает core и пишет запросы в его stdin; ответы и уведомления приходят из stdout. stderr ядра — только диагностика.

Типы полезной нагрузки описаны в [schema/protocol.schema.json](schema/protocol.schema.json) и генерируются в оба потребителя:

```
npm run generate   # → core/src/rpc/protocol.gen.ts, apps/macos/Sources/Luna/Protocol/Protocol.gen.swift
```

Сгенерированные файлы хранятся в репозитории; руками их не правят.

## Запросы (shell → core)

| Метод | params | result |
|---|---|---|
| `core.hello` | — | `HelloResult` |
| `task.submit` | `TaskSubmitParams` | `TaskSubmitResult` |
| `task.cancel` | `TaskCancelParams` | `{}` |
| `task.approve` | `TaskApproveParams` | `{}` |
| `task.list` | — или `TaskListParams` | `TaskListResult` |
| `task.delete` | `TaskDeleteParams` | `TaskDeleteResult` |
| `task.clear` | `{}` | `TaskClearResult` |
| `agents.list` | — | `AgentListResult` |
| `agents.steps` | `AgentStepsParams` | `AgentStepsResult` |
| `agents.approve` | `AgentApproveParams` | `{}` |

`TaskSubmitParams.context` — то, что shell снял в момент вызова панели (`TaskContext`: приложение, URL, заголовок, выделение). Core его нормализует: оставляет известные поля, делает однострочными `app`, `url` и `title`, ограничивает длину.

### Модель

`TaskSubmitParams.model` — модель для этой задачи. Для протокола это непрозрачная строка: её смысл знает исполнитель (для Claude Code — алиас `opus`/`sonnet`/`haiku` или полный идентификатор вроде `claude-opus-4-8[1m]`). Core принимает непустую строку из букв, цифр и знаков `._:[]/-`, не длиннее 100 символов и не начинающуюся со знака (значение попадает в аргументы CLI), иначе — `InvalidParams` («invalid model»). Не передана — модель по умолчанию исполнителя: `LUNA_CLAUDE_MODEL`, затем настройки самого CLI.

`TaskInfo.model` — модель, на которой выполняется задача: как выбрана при отправке, а когда исполнитель сообщил точную — она (алиас `sonnet` → `claude-sonnet-4-6`). Поля нет, пока модель по умолчанию ещё не известна. Новая точная модель уходит в ближайшем `task.progress`, `task.done` или `task.failed` — отдельного уведомления нет; в истории модель сохраняется.

### Уровень разрешений

`TaskSubmitParams.permission` — уровень разрешений исполнителя для этой задачи (`PermissionLevel`): `manual` — спрашивать всё, что исполнитель не считает безопасным сам; `edit_automatically` — править файлы без вопросов, команды спрашивать. Уровень — настройка Luna, что именно спрашивать на нём, решает исполнитель. Не передан — `manual`. Какие уровни исполнитель поддерживает, видно в `core.hello`: `ExecutorStatus.permissionLevels` (набор приходит и при `available: false`). Значение не из перечисления — `InvalidParams` («invalid permission»), уровень, которого исполнитель не объявил, — `InvalidParams` («permission not supported by <executor>»): исполнитель не получает больше выбранного и уровень не подменяется. С `followUpOf` уровень можно передать — это уровень уточнения, а не исходной задачи; без него уточнение идёт на `manual`. Задача, касавшаяся веба, идёт только на чтение на любом уровне. В `TaskInfo` уровня нет.

### Диалог

Уточнение — новая задача того же диалога: `task.submit` с `TaskSubmitParams.followUpOf` — id задачи, которую оно продолжает. Исполнитель продолжает свою прежнюю сессию в прежней рабочей директории; в промпт идёт только текст уточнения, экран заново не захватывается. Если исполнитель прежнюю сессию не нашёл, core один раз перезапускает уточнение новой сессией в той же директории и отправляет переписку заново: контекст первой задачи диалога, прежние вопросы и ответы (`done` с непустым `result`) и уточнение. Задача остаётся той же и `running`, перед перезапуском приходит `task.progress`; промежуточной ошибки нет. Вместе с `followUpOf` поля `context` и `executor` не передаются. `model` можно: она задаёт модель уточнения (диалог и сессия исполнителя остаются теми же); без неё уточнение идёт на модели продолжаемой задачи (`TaskInfo.model` точки продолжения, если она есть и проходит ту же проверку).

`TaskInfo.threadId` — id первой задачи диалога; у задачи без уточнений он равен её `id`. У уточнения — `threadId` и `executor` продолжаемой задачи.

Продолжить можно только последнюю задачу диалога со статусом `done` и с `sessionId`: после неё в диалоге могут быть лишь `failed` и `cancelled`, кроме `failed` с видом `session_not_found` (сессия исполнителя не сохранилась, а переписку отправить заново нечем — в диалоге нет ни одного сохранённого ответа; такой диалог не продолжается), и в диалоге нет задачи `queued` или `running`. Иначе — ошибка `InvalidParams`.

### Поиск и удаление

`task.list` без params (или с пустым, из одних пробелов `query`) отдаёт активные задачи и последние завершённые, всего не больше 200. С `TaskListParams.query` — задачи, у которых `prompt` или `result` содержит запрос целиком как подстроку без учёта регистра (в том числе кириллица; `%`, `_` и `\` — обычные символы), по всей истории, не больше 200 совпавших, новые первыми, — вместе с остальными задачами их диалогов, чтобы диалог показывался целиком.

`task.delete` удаляет диалог задачи `taskId` целиком: записи всех его задач в истории и их рабочие директории внутри каталога данных; `deleted` — id удалённых задач. Неизвестная задача — `{ deleted: [] }`. В диалоге есть задача `queued` или `running` — `InvalidParams`, ничего не удаляется. `task.clear` удаляет все диалоги без таких задач. Удаление необратимо; сессии исполнителя (история Claude Code) не трогаются. Событий об удалении нет.

### Агенты

Сессии агентов, запущенные не Luna (в редакторах и терминалах), core находит сам и только читает; задач Luna среди них нет. `agents.list` отдаёт живые сессии: проекты по алфавиту, внутри проекта — по времени старта. `AgentSession.state`: `working` — агент занят (`activity` — чем), `waiting` — ждёт человека (`waitingFor` — чего, словами агента), `idle` — ход завершён. `AgentSession.host` — приложение, в окне которого идёт сессия: редактор (`ide`, с папкой окна `workspace`) или терминал (`terminal`, с `tty`); `openUrl` — ссылка, по которой редактор открывает вкладку именно этой сессии. `AgentSession.model` — модель последнего ответа агента в журнале сессии, как её записал агент (`claude-opus-5-5`); пока агент не отвечал или журнал не прочитан, поля нет, а служебные ответы без обращения к модели (`<synthetic>`) его не затирают. Менять модель чужой сессии из Luna нельзя. Переход к окну выполняет shell.

`AgentSession.trail` — несколько последних шагов сессии: по ним shell рисует превью работы на плитке, не запрашивая ленту. У шага `tool` есть род инструмента (`AgentStep.tool`: `read`, `edit`, `shell`, `mcp`…) и цель (`target`: имя файла, подпись команды); род — строка, незнакомый shell показывает общим значком.

`agents.steps` — последние шаги сессии, старые первыми: запросы человека, вызовы инструментов, текст агента. С `detail: true` — подробная лента для окна сессии: шагов больше, текст длиннее и с переносами строк. Неизвестная сессия — пустой список.

`AgentSession.approval` (`ApprovalRequest`, тот же тип, что у `TaskInfo.approval`) — действие, которое чужая сессия ждёт от человека. Источник — не файлы сессии, а хук Claude Code `PermissionRequest`, который поставил сам пользователь (`core.hello`: `agentHookPath` — путь к обёртке хука в каталоге данных; нет — ядру не удалось её создать). Без хука поля нет. Показан самый ранний из ждущих запросов сессии; следующий появляется после ответа. Диалог в терминале сессии остаётся, отвечать можно и там: ответ в терминале снимает запрос (поле исчезает из `agents.changed`). Отдельного уведомления нет — запрос приходит обычным `agents.changed`.

`agents.approve` — ответ человека на `AgentSession.approval`: `sessionId`, `approvalId` этого запроса и `allow`. Результат `{}`; после него приходит `agents.changed` со снимком без `approval`. Неизвестная сессия, сессия без запроса или устаревший `approvalId` (в том числе ответ, который в терминале дали раньше) — `InvalidParams`.

## Уведомления (core → shell)

`task.started`, `task.progress`, `task.needs_approval`, `task.done`, `task.failed`, `task.cancelled` — у всех params `TaskEventParams`: полный снимок задачи. Shell обновляет задачу по `id`, не полагаясь на порядок событий.

`task.needs_approval` — исполнитель остановился перед действием и ждёт ответа человека: снимок задачи `running` с `TaskInfo.approval` (`ApprovalRequest`: инструмент, вид действия, путь, подробности). Ответ — `task.approve` с `taskId`, `approvalId` этого запроса и `allow`; после него приходит `task.progress` со снимком без `approval`. Неизвестная задача, задача без ожидания или устаревший `approvalId` — `InvalidParams`.

`agents.changed` — params `AgentsEventParams`: полный список живых сессий. Приходит при любом изменении списка и только после первого `agents.list`: им shell подписывается.

Когда stdin закрывается, core отменяет активные задачи и завершается.
