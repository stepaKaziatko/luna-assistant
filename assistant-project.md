# Персональный ИИ-ассистент (рабочее название: Assistant)

## 1. Общее положение

### Идея
Десктопный ассистент, вызываемый глобальным хоткеем в любой момент работы. Он понимает текущий контекст (активное приложение, URL, выделенный текст), принимает короткий запрос, выполняет его в фоне и возвращает результат, не перекрывая экран и не забирая фокус.

### Ключевой сценарий
1. Пользователь открыл репозиторий на GitHub в браузере.
2. Нажимает хоткей, и сверху по центру появляется компактная панель ввода.
3. Пишет: «дай короткую сводку об этом репозитории».
4. Ассистент снимает контекст (URL, title), ставит задачу в очередь, и панель скрывается.
5. Пользователь продолжает работать.
6. По готовности в pill-индикаторе появляется сигнал; по клику или хоткею раскрывается ответ.

### Принципы
- **Подписки, а не API.** Основные исполнители — Claude Code и Codex CLI, авторизованные через существующие подписки (Claude Pro/Max, ChatGPT Plus/Pro). API-ключи остаются опциональным фолбэком.
- **Ассистент — оркестратор, а не модель.** Он собирает контекст, выбирает исполнителя, делегирует, следит за прогрессом и доставляет результат. Своего агентного цикла с tool calling на старте нет.
- **Не красть фокус.** Ни одно окно ассистента не активирует приложение без явного действия пользователя.
- **Фон по умолчанию.** Любой запрос — это задача в очереди. Параллельные задачи поддерживаются с первого дня.
- **macOS-first.** Кроссплатформенность закладывается в архитектуру ядра, но не в UI (см. раздел 4).

### Не-цели (на первом этапе)
- Собственный агентный цикл и собственные тулзы.
- Голосовой ввод.
- Действия в системе (запись файлов, shell) без ведома человека: по умолчанию Luna спрашивает разрешение на каждое, а без вопроса идут только правки файлов, и только на уровне `edit_automatically`, который пользователь выбирает сам (см. раздел 3.7).
- Распространение как продукта третьим лицам (см. риски в разделе 3.7).

## 2. UI

### 2.1 Компоненты
| Компонент | Назначение |
|---|---|
| **Pill** | Постоянный минимальный индикатор вверху по центру экрана. Показывает состояние: idle / N задач в работе / есть готовый результат / нужно подтверждение. |
| **Input panel** | Раскрывается из pill по хоткею. Поле ввода, чип с захваченным контекстом (иконка приложения + домен/заголовок), выбор исполнителя (по умолчанию «авто»). |
| **Result card** | Раскрывается по клику на pill или хоткею. Markdown-ответ, кнопки: копировать, продолжить диалог (follow-up), открыть полностью. |
| **Task list** | Список активных и завершённых задач с прогрессом («читает README…», «анализирует структуру…»). |
| **Approval prompt** | Блок «Разрешить / Отклонить» в карточке диалога и в карточке и окне чужой сессии агента, когда исполнитель хочет выполнить действие, которое его режим не пропускает без вопроса. Показывает действие целиком: инструмент, путь к файлу или команду без обрезки. Панель сама не открывается: запрос заметен по шторке, счётчику и сигналу. |
| **Settings** | Хоткеи, исполнители и их статус авторизации, правила роутинга, уровень разрешений исполнителя. |

### 2.2 Поведение окон (macOS)
- Все окна — `NSPanel` со стилем `.nonactivatingPanel`: ввод работает без перехвата фокуса у браузера.
- `level = .statusBar`, `collectionBehavior = [.canJoinAllSpaces, .fullScreenAuxiliary]`: видно на всех рабочих столах и поверх полноэкранных приложений.
- Pill на мониторе с курсором. На MacBook с вырезом остров — продолжение выреза: чёрная фигура с вогнутыми плечами, которая плавно переходит в строку меню; в покое она чуть шире выреза, а события выходят крыльями слева и справа от камеры, под камерой ничего не прячется. На остальных мониторах — псевдо-остров той же формы с плечами высотой со строку меню, по центру верхнего края. Раскрытые панели (вопрос, список задач, ответ, агенты, блок под курсором) — та же фигура, которая вырастает из выреза вниз: содержимое начинается под полосой выреза или строки меню, тень — только снизу и по бокам. Не делать функциональность зависимой от выреза.
- Остров виден и над полноэкранными приложениями; кому он мешает — режим «В фоне» (`islandMode`): в покое острова нет, он появляется по событию. На MacBook с вырезом над полноэкранным приложением остров стоит в покое без крыльев — он не шире выреза с запасом. Это же правило — для будущих оболочек Linux и Windows.
- Остров стоит поверх строки меню и не мешает ей: мышь окно принимает только над фигурой с плечами, остальное прозрачно, и клики уходят пунктам меню и значкам рядом. Наведение и клик считаются по контуру фигуры, а не по прямоугольнику с запасом.
- Готовый результат **не всплывает автоматически**: pill меняет состояние (пульс/точка), раскрытие только по действию пользователя. Опционально — системное уведомление, если пользователь давно не смотрел на pill. Запрос подтверждения ведёт себя так же: шторка зовёт и звучит сигнал, но панель открывает только человек.
- Esc закрывает любую панель; повтор хоткея при открытой панели — тоже закрывает.

### 2.3 Состояния pill
```
idle → input → running(n) → done(n) | needs_approval | error
```
Несколько задач: pill показывает агрегированное состояние, приоритет отображения: `needs_approval > error > done > running`. В `needs_approval` входят задачи Luna, которые ждут ответа на запрос, и сессии других агентов, чей запрос пришёл через хук; сессии, которые ждут человека без запроса, считаются отдельно («ждут вас») и стоят ниже ошибок.

### 2.4 Хоткеи (дефолт, настраиваемые)
| Действие | Хоткей |
|---|---|
| Вызвать ввод с контекстом | `⌥ Space` |
| Открыть последний результат; если ждёт запрос подтверждения — самый ранний из них (повторное нажатие закрывает панель, не отвечая) | `⌥ ⇧ Space` |
| Список задач | `⌥ ⌘ Space` |

### 2.5 Захват контекста при вызове
Снимается **в момент нажатия хоткея**, до показа панели:
- `app`: bundle id и имя активного приложения.
- `url`, `title`: для Safari/Chrome/Arc через AppleScript/JXA.
- `selection`: выделенный текст через Accessibility API (фолбэк — симуляция `⌘C` с восстановлением буфера).
- `page_text` (опционально): текст страницы через расширение браузера (фаза 3).

Пользователь видит захваченный контекст чипом и может его убрать перед отправкой.

## 3. Интеграция с ИИ-провайдерами

### 3.1 Исполнители (executors)
| Исполнитель | Авторизация | Сильные стороны | Режим вызова |
|---|---|---|---|
| **Claude Code** | Подписка Claude Pro/Max (`claude` → login) | Ресерч, работа с кодом, веб-инструменты (WebFetch/WebSearch), длинный контекст | `claude -p` (headless) |
| **Codex CLI** | Подписка ChatGPT Plus/Pro (`codex login`) | Работа с кодом, анализ репозиториев, sandbox | `codex exec` (non-interactive) |
| **Qwen (локально)** | Не нужна (Ollama/LM Studio) | Быстрые простые задачи: перефразировать, перевести, сжать уже имеющийся текст. Приватность. | OpenAI-совместимый API `localhost:11434/v1` |
| **API (опционально)** | API-ключи Anthropic/OpenAI | Фолбэк при исчерпании лимитов подписки | HTTP API |

Ядро не реализует логику агентов — оно запускает CLI как подпроцессы и разбирает их потоковый вывод.

### 3.2 Делегирование: контракт задачи
Ядро формирует для исполнителя единый промпт:

```
<context>
app: Google Chrome
url: https://github.com/owner/repo
title: owner/repo: Short description
selection: (пусто)
</context>

<task>
дай короткую сводку об этом репозитории
</task>

<output_requirements>
- Ответ на языке запроса.
- Markdown, не длиннее ~200 слов, если пользователь не попросил иначе.
- Только итог, без описания своих шагов.
</output_requirements>
```

Системные требования к формату передаются через `--append-system-prompt` (Claude Code) или в теле промпта (Codex).

### 3.3 Вызов исполнителей

**Claude Code**
```bash
# промпт — через stdin
claude -p \
  --output-format stream-json --verbose \
  --setting-sources "" --disable-slash-commands --strict-mcp-config \
  --mcp-config "$BRIDGE_CONFIG" \
  --permission-prompt-tool mcp__luna__approve \
  --settings "$HOOK_SETTINGS" \
  --permission-mode default \
  --tools "WebFetch,WebSearch,Read,Glob,Grep,Write,Edit,NotebookEdit,Bash" \
  --allowedTools "WebFetch,WebSearch,Read,Glob,Grep" \
  --append-system-prompt "$FORMAT_RULES"
# уровень edit_automatically: --permission-mode acceptEdits --add-dir "$HOME"
# продолжение диалога: те же флаги и --resume "$SESSION_ID"
```

- `--setting-sources ""` и `--disable-slash-commands` — без пользовательских настроек, `CLAUDE.md`, навыков, плагинов и команд: быстрее старт, меньше расход лимита, предсказуемый набор инструментов.
- `--strict-mcp-config` и `--mcp-config` — единственный MCP-сервер задачи это мост Luna; через него CLI спрашивает разрешение (`--permission-prompt-tool`). `--safe-mode` не используется: он отключает и MCP, а значит, и мост.
- `--settings` — хук `PreToolUse` на запись и команды: он держит запрет записи после обращения к вебу (раздел 3.7) раньше, чем режим CLI пропустит правку без вопроса.
- `--permission-mode` задаёт уровень разрешений (раздел 3.7): `default` для `manual`, `acceptEdits` для `edit_automatically`. На втором уровне `--add-dir` расширяет каталог правок без вопроса до домашней папки.
- `--tools` делает запись и `Bash` доступными, `--allowedTools` по-прежнему разрешает заранее только чтение: всё остальное спрашивается через мост.
- Запуск «только чтение» (диалог, который касался веба): `--tools` — только чтение, без моста, хука и `--add-dir`.

**Codex CLI**
```bash
codex exec --json --sandbox read-only --skip-git-repo-check -C "$WORKDIR" "$PROMPT"
# продолжение диалога:
codex exec resume "$SESSION_ID" "$FOLLOWUP"
```

> Флаги CLI быстро меняются — сверять с актуальной документацией при реализации и закрыть адаптер тестом на парсинг вывода.

**Qwen (Ollama)**
```http
POST http://localhost:11434/v1/chat/completions
```

### 3.4 Рабочая директория задачи
- Каждая задача получает `~/Library/Application Support/Assistant/tasks/<task_id>/`.
- Для GitHub-репозиториев: `git clone --depth 1` в рабочую директорию, и исполнитель запускается с `cwd` в клоне. Анализ по реальному коду точнее и дешевле, чем скрейпинг страницы.
- Приватные репозитории работают через существующие git-креды пользователя (`gh auth`).
- Очистка рабочих директорий по TTL (например, 24 часа).

### 3.5 Роутинг
Порядок принятия решения:
1. **Явный выбор**: префикс в запросе (`@claude`, `@codex`, `@local`) или выбор в UI.
2. **Правила**:
   - URL на github.com/gitlab или запрос про код → Codex или Claude Code (настраиваемый приоритет).
   - Ресерч веб-страниц, сводки, сравнения → Claude Code.
   - Есть `selection` + короткая операция над ним (перевести, переписать, сжать) → Qwen локально.
3. **Дефолт**: настраиваемый исполнитель (рекомендуется Claude Code).

На старте роутинг — только правила. LLM-классификатор намерений (на локальном Qwen) — позже и только если правила реально не справляются: он добавляет задержку к каждому запросу.

### 3.6 Фолбэк и лимиты
- Лимиты подписок оконные (например, 5-часовые и недельные) и **общие с чат-приложениями** — интенсивная работа в чате уменьшает квоту ассистента и наоборот.
- Ошибка лимита/авторизации от исполнителя → задача автоматически перезапускается на следующем исполнителе по цепочке (`claude-code → codex → api`), пользователь видит, кто выполнил задачу.
- Settings показывает статус авторизации каждого CLI и подсказку `claude login` / `codex login`.

### 3.7 Безопасность и права
- У исполнителя есть **уровень разрешений** — настройка Luna, по умолчанию `manual`:
  - `manual` — исполнитель спрашивает человека обо всём, что его режим не считает безопасным сам: запись файлов, правки, команды. Чтение идёт без вопроса.
  - `edit_automatically` — правки файлов в домашней папке без вопроса; команды и защищённые пути (`.git`, `.claude` и подобные) по-прежнему спрашиваются.
- Права **наследуются от коннектора**: Luna только передаёт выбранный уровень (`task.submit.permission`, режим CLI) и показывает вопросы, которые задаёт исполнитель. Своих списков команд, путей и политик у Luna нет: что спрашивать на уровне, решает CLI. Какие уровни исполнитель поддерживает, он сообщает сам (`ExecutorStatus.permissionLevels`); уровень, которого он не объявил, — ошибка, а не подмена. Для Codex, когда появится адаптер, исходный режим — `--sandbox read-only`.
- Подтверждение показывает действие целиком, без обрезки: путь файла или команду полностью. Команда, которую человек не прочтёт до конца (длиннее 20 000 знаков), отклоняется без вопроса. Ответ человека — «Разрешить» или «Отклонить»; отмена задачи, выход из Luna и сбой исполнителя отклоняют ждущие запросы, действие не выполняется.
- Контент веб-страниц считается недоверенным (prompt injection), и это жёсткое исключение из уровней: диалог, в котором был контекст со страницы (`url`) или исполнитель обращался к `WebFetch`/`WebSearch`, идёт только на чтение на любом уровне. Запись и команды в нём отклоняются без показа человеку; признак хранится в истории и переходит на уточнения диалога.
- Сессии агентов, запущенные не Luna, спрашивают разрешение у Luna только через хук `PermissionRequest`, который ставит сам пользователь; Luna настройки чужого агента не меняет, без хука она за сессиями только наблюдает.
- Подписочные CLI используются **для личного использования** на машине владельца подписки. Распространение ассистента другим пользователям с опорой на их подписки нужно отдельно сверить с условиями Anthropic и OpenAI.

### 3.8 Прогресс
Потоковые события CLI (`stream-json` / `--json`) парсятся в нормализованные события ядра:
```
task.started | task.progress | task.needs_approval | task.done | task.failed | task.cancelled
```
Все они несут снимок задачи (`TaskInfo`). `task.progress` даёт человекочитаемый статус для task list («читает README.md»).

`task.needs_approval` — исполнитель остановился перед действием: снимок задачи `running` с `TaskInfo.approval` (инструмент, вид действия, путь или команда). Ответ человека — запрос `task.approve` с `allow`; после него приходит `task.progress` без `approval`, а если у задачи есть следующий запрос — снова `task.needs_approval`. Запросы чужих сессий агентов идут в `agents.changed` (`AgentSession.approval`), ответ — `agents.approve`. Подробности — в [protocol/README.md](protocol/README.md).

## 4. Верхнеуровневая структура

### 4.1 Архитектура
```
┌──────────────────────┐   JSON-RPC (stdio)   ┌───────────────────────────┐
│  Shell (UI, native)  │ ◄──────────────────► │  Core (daemon)            │
│  macOS: Swift/AppKit │                      │  TypeScript / Node        │
│  - хоткеи            │                      │  - очередь задач          │
│  - панели, pill      │                      │  - роутинг                │
│  - захват контекста  │                      │  - адаптеры исполнителей  │
└──────────────────────┘                      │  - workdir, история       │
                                              └─────────┬─────────────────┘
                                                        │ subprocess / HTTP
                                    ┌───────────────────┼──────────────────┐
                                    ▼                   ▼                  ▼
                               claude -p           codex exec        Ollama / API
```

Shell запускает Core как дочерний процесс и общается через stdio JSON-RPC. Отдельный сервер с портом не нужен.

### 4.2 Стек
| Слой | Технология | Почему |
|---|---|---|
| UI shell (macOS) | Swift, SwiftUI + AppKit (`NSPanel`) | Неактивирующие панели, хоткеи, AppleScript и Accessibility — нативно и без костылей |
| Хоткеи | `KeyboardShortcuts` (sindresorhus) | Готовое решение с UI записи хоткея |
| Core | TypeScript (Node) | Официальные SDK Claude Agent / Codex / MCP — на TS; удобная работа с потоковым JSON и подпроцессами |
| Протокол | JSON Schema → генерация типов (Swift и TS) | Единый источник контракта между shell и core |
| Хранилище | SQLite (история задач, настройки) | Локально, без зависимостей |
| Локальные модели | Ollama | OpenAI-совместимый API |
| Расширение браузера (фаза 3) | Chrome MV3 + native messaging | Надёжный текст страниц и авторизованный контент |

### 4.3 Кроссплатформенность
- **Core** кроссплатформенный по построению: Node, CLI исполнителей есть на macOS/Linux/Windows.
- **Shell** — отдельный нативный на каждую ОС. Захват контекста, поведение окон и права доступа слишком платформенно-специфичны; кроссплатформенный UI-фреймворк (Tauri/Electron) сэкономил бы только вёрстку, но не эту часть.
- Windows/Linux shell не делаются, пока macOS-версия не стабилизирована. Протокол shell↔core — единственное, что нужно для их будущего добавления.

### 4.4 Репозитории
**Один монорепозиторий.** Shell и core меняются синхронно через общий протокол; раздельные репозитории на этом этапе дадут только рассинхрон версий.

```
assistant/
├── apps/
│   └── macos/                 # Swift shell (Xcode project)
├── core/
│   ├── src/
│   │   ├── rpc/               # JSON-RPC сервер на stdio
│   │   ├── tasks/             # очередь, состояния, история
│   │   ├── routing/           # правила выбора исполнителя
│   │   ├── executors/
│   │   │   ├── claude-code/
│   │   │   ├── codex/
│   │   │   ├── ollama/
│   │   │   └── api/
│   │   ├── context/           # нормализация контекста, workdir, git clone
│   │   └── prompt/            # сборка промптов исполнителям
│   └── test/                  # фикстуры потокового вывода CLI
├── protocol/
│   └── schema/                # JSON Schema + генерация типов
├── extensions/
│   └── browser/               # фаза 3
└── docs/
```

Разделение на несколько репозиториев имеет смысл только при появлении второй платформы с отдельной командой или при публикации core как самостоятельного пакета.

## 5. Этапы

| Фаза | Содержание | Критерий готовности |
|---|---|---|
| 1 | Shell: хоткей, pill, input panel, result card. Core: один исполнитель (Claude Code), синхронный вызов | Вопрос из панели → ответ в карточке |
| 2 | Захват контекста (Safari/Chrome URL, title, selection), фоновая очередь, параллельные задачи, прогресс | Сценарий «сводка репозитория» работает без ожидания в UI |
| 3 | Codex и Ollama адаптеры, роутинг по правилам, фолбэк по лимитам, git clone для репозиториев | Задачи автоматически уходят нужному исполнителю |
| 4 | Follow-up диалоги (resume сессий), история, approval prompts — сделаны; расширение браузера — впереди | Запись файла по просьбе проходит через подтверждение, веб-задача записи не получает |

## 6. Риски
| Риск | Митигация |
|---|---|
| Изменение флагов/формата вывода CLI | Адаптер на исполнителя + тесты на фикстурах вывода, пиннинг версий CLI |
| Изменение условий использования подписок в сторонних инструментах | Фолбэк на API-ключи, адаптерная архитектура |
| Исчерпание лимитов подписки | Цепочка фолбэка, отображение исполнителя и ошибки лимита |
| Ненадёжный захват контекста в разных браузерах | Начать с Chrome/Safari, расширение браузера как основной путь в фазе 3 |
| Prompt injection из веб-контента | Диалог, который касался веба, идёт только на чтение на любом уровне; по умолчанию `manual` — approval для записи и команд |
